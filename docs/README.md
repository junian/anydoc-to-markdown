# AnyDocToMarkdown

.NET libraries for converting documents (Word, PowerPoint, Excel, OpenDocument,
RTF, EPUB, CSV, and PDF) to clean GitHub-Flavored Markdown, backed by the
**anydoc** Rust engine. Unofficial wrapper of `anydoc` for .NET.

Two packages ship from this repository:

- **`AnyDocToMarkdown`** — the native binding (`netstandard2.0`), bundling the
  Rust engine as a native library for **Windows x86/x64/arm64, macOS x64/arm64,
  and Linux x64/arm64**. It works on .NET (Core) 3.0+ and later runtimes.
- **`AnyDocToMarkdown.BlazorWasm`** — a WebAssembly binding for Blazor WASM
  apps that runs the same engine compiled to `wasm32-unknown-unknown`; no native
  library is loaded.

The document model, the `Format` enum, and the error surface are shared source,
so both packages expose the same `AnyDocToMarkdown.*` types.

## Usage: native

```csharp
using AnyDocToMarkdown;

// Construct once and reuse for every conversion.
// Instances are thread-safe and hold no disposable state.
var anydoc = new AnyDocToMarkdownConverter();

// From a file path (format detected from the content):
string markdown = await anydoc.ToMarkdownAsync("report.docx");

// From bytes, with the format detected from the content:
string fromBytes = await anydoc.ToMarkdownBytesAsync(bytes);

// Or name it, which signature-less formats (CSV) needs:
string fromCsv = await anydoc.ToMarkdownBytesAsync(bytes, Format.Csv);

// Or stop at the document model, which also carries embedded assets:
Document document = await anydoc.ToDocumentAsync(bytes);
```

Synchronous variants (`ToMarkdown`, `ToMarkdownBytes`, `ToDocument`) behave the
same way when you are not in an `async` context.

### Format detection

```csharp
Format? byBytes  = anydoc.DetectFormat(bytes);              // content signature
Format? byExt    = anydoc.DetectFormatByExtension(".pptm"); // => Format.Pptx
Format? byPath   = anydoc.DetectFormatByPath("sheet.csv");  // => Format.Csv
```

### Errors

Failures throw `AnydocException`, whose `Kind` (a `ConvertErrorKind`) names the
reason the same way the Node and Python bindings do:

```csharp
try
{
    string md = anydoc.ToMarkdown(bytes, Format.Docx);
}
catch (AnydocException e)
{
    switch (e.Kind)
    {
        case ConvertErrorKind.Unsupported:   // scanned PDF, unknown format
        case ConvertErrorKind.Malformed:     // structurally unusable document
        case ConvertErrorKind.Encrypted:     // password-protected
        case ConvertErrorKind.ResourceLimit: // a fixed safety limit was crossed
        case ConvertErrorKind.MissingPart:   // a required part is absent
        case ConvertErrorKind.Io:            // the file could not be read
    }
}
```

The document model (`AnyDocToMarkdown.Model`) encodes every block, inline,
list, table grid, note, and embedded asset, mirroring the Node and Python
bindings (`Kind` string discriminants, `NoteId`, `MediaType`, etc.).

## Usage: Blazor WebAssembly

For client-side Blazor there is a sibling package,
`AnyDocToMarkdown.BlazorWasm`, that runs the same engine compiled to
WebAssembly. No native library is loaded, so a `browser-wasm` publish needs no
RID-specific runtime: the WASM engine ships as static web assets.

```csharp
using AnyDocToMarkdown;
using Microsoft.JSInterop;

// Injected into a Blazor component or service:
var anydoc = new AnyDocToMarkdownConverter(jsRuntime);

// A browser has no filesystem, so conversion always starts from bytes and every
// call is async (Blazor WASM has no synchronous JS interop):
byte[] bytes = await httpClient.GetByteArrayAsync("report.docx");
string markdown = await anydoc.ToMarkdownBytesAsync(bytes);
Document document = await anydoc.ToDocumentAsync(bytes);

Format? format = await anydoc.DetectFormatAsync(bytes);
```

One converter instance is enough for the whole app: it instantiates the WASM
module lazily and caches it. The API matches the native package — `Format`,
`ConvertErrorKind`, `AnydocException`, and the `AnyDocToMarkdown.Model` types
are the same shared source — but the sync-named members (`ToMarkdownBytes`,
`ToDocument`, `DetectFormat`, ...) throw `PlatformNotSupportedException`
because Blazor WASM cannot block on JavaScript interop.

## Building

The `anydoc` engine lives in the `libs/anydoc` git submodule. That checkout is
**read-only**: never modify files inside `libs/anydoc`; the native binary, the
[csbindgen](https://github.com/Cysharp/csbindgen)-emitted C# wrapper, and the
WASM outputs are regenerated by the build scripts.

The C# DllImport surface is generated from the Rust FFI with csbindgen
(`cargo build -p anydoc-dotnet`, run by `native/build.rs`), which rewrites
`src/AnyDocToMarkdown/NativeMethods.g.cs`.

### Native binaries and the NuGet package

```sh
sh build.sh            # build the host's native library and pack
sh build.sh --all      # build every supported platform's library
```

Each supported platform's library is laid out under
`src/AnyDocToMarkdown/runtimes/{rid}/native/` — NuGet's native-library
convention — so a single package carries all targets. Cross-compiling to a
target you do not natively develop on needs the Rust target installed
(`rustup target add <triple>`) and a cross-linker; the script prefers
`cargo-zigbuild` (zig) for the Linux and Windows gnu targets. Windows/MSVC
builds are produced on Windows runners.

### WebAssembly engine

```sh
sh build-wasm.sh       # needs wasm32-unknown-unknown target + wasm-bindgen-cli
```

This reads the engine from `libs/anydoc/wasm`, builds it to WASM, and writes
`anydoc_wasm.js` (the wasm-bindgen glue) and `anydoc_wasm_bg.wasm` into
`src/AnyDocToMarkdown.BlazorWasm/wwwroot/`, which the package ships as static
web assets. `wwwroot/anydoc-wasm.js` — the small interop shim the managed
wrapper loads via Blazor's `import` — is checked in and never regenerated.

### Tests

```sh
dotnet test AnyDocToMarkdown.slnx
```

Requires the native library built (for the `AnyDocToMarkdown.Tests` project)
and the WASM artifacts (for `AnyDocToMarkdown.BlazorWasm.Tests`, which stubs
the JS layer).
